MaluOS is a Linux distribution derived from Ubuntu 26.04 LTS (resolute),
designed for both humans and AI agents and centred on the MaluDB memory
database.

This repository holds the distribution layer: the signed APT repository,
metapackages and seeds, branding, installer configuration, ISO build

# Phase 3: MaluOS images built from the seeds

Phase 2 proved the install path with Ubuntu's own root filesystem and a
late-commands package install. Phase 3 makes the root filesystem ours:
built from the seeds, identical across the ISO and the cloud image, and
installable offline.

## Design

```
seeds/*.seed  ->  maluos-* metapackages  ->  MaluOS apt repo
                                                   |
image/profiles/server.pkgs  +  Ubuntu archive  +  PGDG
                                                   |
                 image/build-rootfs.sh  (mmdebstrap, as root)
                                                   |
            build/image/maluos-server.rootfs/  (directory)
                /                 \
 image/build-qcow2.sh         mksquashfs
        |                          |
 maluos-server-26.04-amd64.qcow2   maluos-server.squashfs  --> iso/build-iso.sh
 (cloud-init, BIOS+UEFI)           (default install source on the ISO)
```

**Installer.** The ISO keeps Ubuntu's live installer environment (subiquity)
untouched and adds the MaluOS squashfs as the default entry in
casper/install-sources.yaml. Subiquity copies it to the target disk, installs
the kernel from the ISO pool and applies identity, network and storage. No
installer fork, no snap seeding, and the installed system is exactly the
rootfs we built. Ubuntu's own sources stay selectable in the guided install.

**Offline.** PostgreSQL 18 and the MaluDB packages are inside the squashfs,
so an ISO install no longer needs the network. The late-commands only copy
the on-media repository to /var/lib/maluos/apt and enable the serial console.

**Identity.** maluos-branding diverts os-release, issue and issue.net.
NAME, PRETTY_NAME and VARIANT say MaluOS; ID stays `ubuntu` so cloud-init,
curtin, PGDG scripts and add-apt-repository keep working.

**Cloud image.** GPT with BIOS boot, ESP and ext4 root, grub for both
firmware types with Secure Boot shim, serial console on, cloud-init with
growpart. Boots on Proxmox, KVM, and cloud providers that take qcow2 or raw.

# MaluOS components

A component is something a MaluOS system can carry in addition to the base
memory server: the MaluDB API server, the Business OS kernel, its
applications. The model replaces Ubuntu's "featured snaps" step with
packages, so a component can be chosen at install time, requested at first
boot through cloud-init, or added later, and every path ends in the same
provisioned state.

## Anatomy

| Part | Where | Role |
|---|---|---|
| Metapackage `maluos-<name>` | seeds/<name>.seed -> packages/maluos-meta | What "the component" means in packages |
| Software packages | packages/<pkg> (vendored upstream + debian/) | The code, units, users, config |
| First-boot module | /usr/lib/maluos/components/<nn>-<name>.py, shipped by the package | Provisions the component against the database on first boot or `maluctl provision` |
| Configuration | /etc/maluos/firstboot.yaml `components.<name>` | enabled: true/false, component-specific keys |
| Checks | tests/qcow2-boot-test.sh | The component's acceptance checks on a booted image |

The first-boot engine (maluos-firstboot) runs the core steps, then every
module in /usr/lib/maluos/components in name order with a context (database
name, tenant, psql helper, secrets directory, env-file helpers). A module
returns a JSON summary that lands in /var/lib/maluos/firstboot/done and in
`maluctl status`; a failing module is recorded and does not block the rest.
Modules must be idempotent: `maluctl provision --force` re-runs them all.

## Delivery paths

- **Image profile**: image/profiles/server.pkgs lists what the server rootfs
  carries (today: maluos-server and maluos-api). A profile per variant, or a
  squashfs layer per component in the ISO catalogue, gives install-time choice.
- **cloud-init / autoinstall**: write /etc/maluos/firstboot.yaml with the
  components wanted; packages already in the image are provisioned, absent
  ones are installed from the on-media repository first (planned).
- **Later**: `apt install maluos-<name>` then `maluctl provision --force`
  (planned: `maluctl component add <name>` doing both).

# Releases, keys and hosting

## Cadence

A MaluOS release is a dated build on top of the Ubuntu point release it
derives from: `26.04.YYYYMMDD` (file `VERSION`, tag `vVERSION`). Packages
keep their own Debian versions and flow through the apt repository
continuously; a release is the moment an ISO and a cloud image are built
from a tagged tree, boot-tested, named, checksummed, signed and published.

- Routine: a release whenever a phase or a meaningful fix lands and CI is
  green, at least monthly while the project is moving.
- Rebase: when Ubuntu ships a point release (26.04.2 ...), update the base
  ISO in iso/ and CI, rebuild, release.
- Hotfix: a package fix is just a package publish; it reaches installed
  systems through apt. A new release only when the install media must
  change.

`scripts/release.sh` does the mechanics: checks a clean main, names the
artefacts, writes SHA256SUMS and a clearsigned SHA256SUMS.gpg, generates
RELEASE-NOTES.md from the manifest and the git log, commits VERSION, tags,
pushes, creates the GitHub Release with the cloud image and checksums, and
pushes the ISO to the download host when MALUOS_DOWNLOAD_RSYNC is set (the
ISO is too large for a GitHub release asset). The `release` workflow then
rebuilds the cloud image from the tag in CI, boot-tests it, and attaches
that independently built copy to the same release.

## Signing keys

Two keys, two roles:

| Key | Where | Signs |
|---|---|---|
| Development key (`MaluOS Archive Automatic Signing Key`, no passphrase) | the maintainer's keyring on the build host | the local repository used for image builds and tests |
| Production key (`MaluOS Archive Signing Key (YEAR)`, passphrase, Ed25519, 2-year signing subkey) | signing subkey on the publishing host, primary secret key offline | the public repository and release checksums |

`repo/make-production-key.sh YEAR` creates the production key and exports
its public half into packages/maluos-keyring/keys/. The keyring package
imports every key there, so clients trust both during a transition.

Custody rules:

1. The primary secret key is exported once, stored offline (a USB key in a
   safe, or the password manager's file vault) and removed from the host;
   only the signing subkey remains. Losing the primary means a new key and
   a keyring update; losing the subkey means revoking it with the primary.
2. The passphrase lives in the password manager, never in a file on the
   host; gpg-agent asks for it once per publishing session.
3. Rotation (every two years, or on any suspicion): make the new key, ship
   a maluos-keyring update that carries both public keys signed by the old
   key, switch `MALUOS_SIGNING_UID`, and after one release remove the old
   public key from the package.
4. The development key never signs anything that leaves the LAN.

Two published trees of the same repository, so nothing unattended ever
needs the production passphrase:

| Tree | Signed by | Used by |
|---|---|---|
| `~/.aptly/public/dists,pool` | development key | image builds, local tests, CI |
| `~/.aptly/public/public/dists,pool` | production key | `repo/publish-remote.sh`, which refuses any other signature, and so apt.maluos.com |

#!/bin/bash
# Replicates subiquity's configure_apt step against the ISO's install source
# without booting anything: mount the ISO, overlay its MaluOS squashfs, bind
# the ISO at /cdrom, then run apt-get update inside like the installer does.
# This is the step that failed on the first external install (unsigned pool).
