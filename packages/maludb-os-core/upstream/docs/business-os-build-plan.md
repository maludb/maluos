## Refocus 2026-09-22 — the OS is a kernel

The owner's decision, after reviewing the built platform: **too many business applications were built into the operating system.** The Business OS manages the AI agents, the humans who administer them directly (super-admins), and single sign-on; the applications a business uses are separate Apache/PostgreSQL/PHP/HTMX applications at their own names (`hr.subello.com`), signed in by the kernel from the launcher at `app.subello.com`, each with full MCP coverage and its own expert agent. The design — boundary, hosts, the hand-off token, the directory API, agents, token accounting, registration, the build order and the exact inventory of the cut — is `docs/business-os-integration.md` (live: https://claude.ai/code/artifact/7f923c54-5189-41ee-bdb0-95cd6610ccfa); the application-side contract is the `maludb-os-integration` plugin, 0.2.0.

What it does to this plan: **phases 2, 3 and 4's business slices are removed** (code, screens, tools, manifest, tables — one migration, db/133, drops them) together with the cert-study legacy and the kernel's command bar; phase 1's Contacts/CRM exemplar goes with CRM and **Applications becomes the exemplar slice**; phase 5's people-and-payroll step becomes the HR application; phase 6 (desktop) is **deferred**; phase 7 is restated below with the kernel's build order in front of the installation agent. The Accounting agents (Sasha, Becky, Jack) are kept and re-versioned with duties around the token ledger and its period export. Done-notes below stay as the record of what was built.

## How we build

The plugin's fixed build order governs, adapted for a fork conversion: design the COMPLETE database and memory model for the entire Business OS before writing feature PHP — every module including departments (the four standing ones included), agent employee records, the estate of buildings/offices/desks, the applications registry, the task queue, and the prompt ledger. Features then ship as vertical slices in phase order. The fork means the plugin's auth-and-shell phase is mostly done already; it gets rebranded, not rebuilt.

The order, with its checkpoints:

1. **Design everything** — full schema (one migration file per concern), the question list per module, the MCP tool surface (a question with no tool is unfinished design), and the action manifest (a screen or action missing from it is unreachable by voice — same defect). **Checkpoint: user approves schema + tool surface + manifest before any new PHP.**
2. **Convert the shell** — rebrand, new module navigation, command bar intact. **Checkpoint: user reviews the running shell.**
3. **Vertical slices** in phase order. A slice is done when it has: screens per the design system (no modals, works at 375px), handlers per php-patterns, activity logging on every action, action-manifest registration, MCP tools for its new questions, and — where an agent will touch it — eval cases. **Checkpoint: demo per slice.**

**Model tiering.** Judgment is spent once, up front, on the most capable model; the repetitive majority is replicated by cheaper workers against specs:

| Work | Model class |
| --- | --- |
| Schema, tool surface, manifest, all slice build specs | Planning-class (Opus/Fable) |
| Shell conversion + the first (exemplar) slice | Planning-class |
| Remaining slices | Worker-class (Sonnet), phrased as replication of the exemplar |
| Per-slice conformance review of the diff | Planning-class at low effort |

Workers never improvise: an ambiguous spec stops the slice and escalates as a recorded open question — an invented decision is a defect even when the code works. Every worker slice passes the plugin's mechanical conformance checklist (CSRF + auth + logging on every state change, escaping, id scheme, no modals, manifest registration) plus a short planning-class diff review.

## Front-end migration to React (decided 2026-09-18)

The front end moves from HTMX to **one Next.js/React application**, and the AI Agent View becomes part of it; the full plan is `docs/react-migration-plan.md`. PHP stays as a JSON API — auth, CSRF, authorization, approvals, activity logging and the query functions are kept, and its handlers remain the single write path for people and agents. Day-to-day screens keep the Bootstrap 5.3 look; the Agent View is the home screen, and an Agent View button on selected screens opens a visualisation of that screen's subject. The cert-study legacy screens are not ported and retire at cut-over; their tables stay.

**Feature work on phases 3–6 is frozen until cut-over.** Order: R0 baseline → R1 PHP API foundation → R2 web foundation → R3 Contacts/CRM exemplar in React (**checkpoint: owner approves the exemplar before anything fans out**) → R4 worker-model conversion in four waves → R5 Agent View integration (parallel lane) → R6 cut-over → R7 phases 3–6 resume on the new slice template. Until R6 the existing HTMX UI stays live and every endpoint answers both HTML and JSON.

## Phase 5 — Agent workforce

Goal: the first AI agent is hired into a department, supervised, measured, and doing real work at the Office location. This phase builds the platform's differentiator, so its core pieces are planning-class work.

Build order inside the phase (each step depends on the previous):

1. **Agent-runner interface + harness registry.** The Python service contract every harness implements — job description in, MCP tools attached, telemetry out, budget metered, interrupt/approval hooks. **Hermes Agent harness first** *(2026-09-19, owner's decision — `docs/hermes-integration-plan.md`; conformance-tested at a pinned release, memory and skills on MaluDB)*; **Claude Agent SDK second, and it proved the registry generalizes: one class, one renderer, one tuple entry** *(2026-09-20 — `docs/build-specs/agent-runtime-claude-sdk.md`, conformance `mcp/claude_conformance/`; the owner declined the other two, which have no agent hired on them)*. ## Phase 6 — Desktop beta

Goal: "Ed's Desk" exists — a desktop install that is a location with resident agents, using the office brain plus local files.

4. **Desk runtime.** The same agent-runner + harness registry from phase 5 running on the desk, telemetry shipped to the tenant's prompt ledger; the desk office manager as its orchestrator.
5. **Cross-location tasking.** Brokered requests through the server task queue in both directions, consent grants (standing or one-off), offline queueing with visible status.
6. **Beta packaging.** Windows + macOS builds, auto-update channel, versioned MCP surface check on connect.

**Exit criteria:** from the Office UI, a user asks the desk's agent to summarize a local spreadsheet; the desk owner's standing permission admits it; the result returns through the queue; the whole exchange is visible in the activity log and prompt ledger.

## Rules that apply to every phase

- **No modals, mobile first.** Create/edit/detail are dedicated full pages (React routes after the migration, HTMX until cut-over); every screen works at 375px with no horizontal scroll before it counts as done.
- **Log everything.** Any handler that changes state or renders a screen writes an `activity_log` row; any model call writes a prompt-ledger row. No exceptions, no backfill.
- **Manifest and tools keep pace.** A slice's screens and actions land in the action manifest, and its questions get MCP tools, in the same slice — never "later".
- **Security non-negotiables.** `require_post()` + `verify_csrf()` + authorization check on every state change; all output through `e()`; prepared statements; RLS on member-owned tables; agent tokens are member-scoped, always.
- **Specs live in the repo.** Every slice's build spec goes in `docs/build-specs/` before its slice starts; this plan and the requirements stay synced between the live docs and `docs/`.
- **Evals grow continuously.** Any agent-facing behavior added in any phase adds eval cases; regressions block the change that caused them.
