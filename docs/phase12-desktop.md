# Phase 12: MaluOS Desktop

The server variant is stable (Phases 1 to 10), so the desktop begins. The
desktop is the estate's *desk*: the machine a person works at, where their
agents run while it is online, with local memory. It is built exactly like
the server, from a seed through a metapackage into a rootfs, so the same
scripts, tests, CI and release mechanics apply with `-p desktop`.

## Slice 1 (2026-10-19): the stack, the images, the test

```
seeds/desktop.seed  ->  maluos-desktop (metapackage)
                        + maluos-desktop-branding (from packages/maluos-branding)
image/profiles/desktop.pkgs = ubuntu-minimal + maluos-desktop + maluos-server + kernel, grub, cloud-init
sudo image/build-rootfs.sh -p desktop     -> build/image/maluos-desktop.{rootfs,squashfs,manifest,size}
sudo image/build-qcow2.sh  -p desktop     -> build/image/maluos-desktop-26.04-amd64.qcow2 (8G, BIOS + UEFI)
iso/build-iso.sh           -p desktop     -> build/maluos-26.04.1-desktop-amd64.iso
tests/qcow2-boot-test.sh build/image/maluos-desktop-26.04-amd64.qcow2
sudo tests/iso-apt-check.sh build/maluos-26.04.1-desktop-amd64.iso
```

### Decisions

- **GNOME 50 with Ubuntu's session.** `ubuntu-session`, the Ubuntu shell
  extensions (dock, app indicators, tiling) and the Yaru theme, because
  they are what Ubuntu 26.04 users expect and none of it is trademark use
  (package names and the `ubuntu` session mode are machine-facing). The
  parts of `ubuntu-desktop-minimal` that are Ubuntu-branded programs are
  left out: Software Updater (`update-manager`, `update-notifier`), the
  release upgrader, `ubuntu-report`, `ubuntu-insights`, `whoopsie`/`apport`,
  `ubuntu-docs`. Updates come through unattended-upgrades and apt as on the
  server; a MaluOS updater is a later slice.
- **No snaps.** `snapd` is not installed. That rules out Firefox and
  Chromium from the Ubuntu archive (both are snap wrappers there), so the
  browser is GNOME Web (`epiphany-browser`). Mozilla's own apt repository
  is the way to Firefox later: a second external source like PGDG, with
  its key in maluos-keyring.
- **A desktop is also a memory host.** The image profile adds
  `maluos-server`: PostgreSQL 18, MaluDB, the vault, the gateway, agents
  and first boot, so agents on the workstation have local memory and
  credentials. The API server and the Business OS kernel stay on the
  office; `apt install maluos-desktop` on an existing system does not
  pull PostgreSQL in (the metapackage, not the profile, is what apt sees).
- **Identity by package.** `maluos-desktop-branding` carries everything
  the login screen and the desktop show: `VARIANT="Desktop"` (os-release
  is now a symlink picked by `apply-variant`), the MaluOS logo on the
  greeter, the MaluOS wallpapers (light and dark, generated by
  packages/maluos-branding/tools/make-branding.py and committed), the
  distributor icon that Settings > About shows (`LOGO=maluos-logo`), the
  boot splash watermark (diverting plymouth-theme-spinner's link to
  Ubuntu's logo, then `update-initramfs -u`), and
  the session entry renamed from "Ubuntu" to "MaluOS" through a
  diversion of ubuntu-session's file (file name, Exec and DesktopNames
  are kept: the shell mode and the `:ubuntu` gsettings overrides key on
  them). The overrides live in `20_maluos-desktop.gschema.override`,
  which sorts after ubuntu-settings' file and so wins.
- **Same installer, same screens.** The desktop ISO is the Ubuntu Server
  live installer with the desktop squashfs as its default source
  (`variant: server` in the catalogue keeps the text installer flow; the
  install source, not the variant, decides what is installed). The late
  command for the desktop sets `quiet splash` instead of the serial
  console. A graphical live session and installer belong with Phase 11's
  own installer.
- **dracut is named in the profile.** The first desktop rootfs had no
  initramfs at all: the kernel package only recommends an initramfs
  builder, and `ubuntu-minimal` (unlike `ubuntu-server-minimal`) pulls
  none in. The profile lists dracut, Ubuntu 26.04's builder; the branding
  package's `update-initramfs -u` goes through dracut's shim.
- **cloud-init stays in the image** so the qcow2 boots from a NoCloud
  seed in tests and on VM hosts; on a laptop with no datasource it costs a
  second at boot. Dropping it from ISO installs is an open item.

### Test

`tests/qcow2-boot-test.sh` now gates the API and Business OS sections on
the packages being present and adds a desktop section when
`maluos-desktop` is installed: graphical target, gdm active, a gnome-shell
process (the greeter, under software rendering in QEMU), no snapd or
Ubuntu-branded updaters, `VARIANT="Desktop"`, the session entry, the
assets, the compiled overrides, and the login screen logo and session
background read back through gsettings. The desktop VM gets 3 GB and 4
vCPUs. CI builds and boot-tests the desktop on demand (`images` workflow
input `desktop`).

## Slice 2 (2026-10-19): the agent-aware session

```
packages/maluos-session  ->  maluos-desktop-session (in seeds/desktop.seed)
  /usr/lib/maluos/maluos-desktop-session        the session service (python3, Gio), com.maluos.Session
  /usr/lib/systemd/user/maluos-desktop-session.service   enabled for every user, WantedBy graphical-session.target
  /usr/share/dbus-1/services/com.maluos.Session.service  D-Bus activation (the extension's proxy starts it)
  /usr/share/gnome-shell/extensions/maluos-session@maluos.com/   the indicator
  /usr/share/glib-2.0/schemas/30_maluos-session.gschema.override  enables it in the MaluOS session
maluos-desktop-session --once                   the state as JSON, for tests and debugging
```

The desk knows things a laptop does not: which agents live here, whether
the gateway and its backends are up, how much of the user's model budget
is spent, what the vault holds for them, and which memory host this is.
Slice 2 puts that knowledge in the session.

**The session service.** One process per logged-in user, D-Bus activated
and owned by `systemd --user`. It reads the agents from
`/etc/maluos/agents` and their units from systemd on the system bus (the
unit list is readable by anyone; it subscribes to `JobRemoved` so a
start or stop is seen within two seconds), the gateway at
`/run/maluos/gateway.sock` (`health`, `status`, `whoami`, `routes`) and
the vault at `/run/maluos/vault.sock` (`whoami`, `secrets`,
`compartments`, `delegations`, `ledger?event_like=alert.%`), all as the
session user: peer-credential identity means the service sees exactly
what the user may see, with no token anywhere in the session. The gateway's
`whoami` now carries the caller's own spend for the day and the month
(maluos-gateway 0.3.2), so the budget needs no operator rights. The memory
host comes from first boot's summary in `/var/lib/maluos/firstboot/done`.
Every 20 seconds, or when systemd says an agent job finished, the service
rebuilds one JSON document (`GetState`, signal `StateChanged`) and
compares it with the last: an agent created, running, stopped, failed or
removed, the gateway or a backend going away or coming back, the user's
budget crossing its warning or its limit, and a new alert row for the
user in the ledger each become a desktop notification
(`org.freedesktop.Notifications`, so they work in any session, not only
with the extension). `AgentAction(name, start|stop|restart)` forwards to
systemd with interactive authorisation: the user's own polkit prompt
decides, as it would for `systemctl start`.

**The indicator.** A GNOME Shell extension (ESM, GNOME 50) with a panel
icon and a menu: host and memory tenant; the agents, each with its unit
state and a submenu (start or stop, restart, logs in a terminal); the
gateway with healthy backends and the queue, a backend list with loaded
models and errors; the user's principal and budget; recent calls; the
vault's secrets, compartments and delegations; the latest alerts. The
icon turns amber when a backend is down or the budget is nearly used, red
when an agent has failed or the budget is exhausted, and dims when the
gateway is not on this host. It renders only; everything comes over the
session bus from the service, so a crash in the data path cannot take the
shell down with it. It is enabled through `enabled-extensions` in a
`:ubuntu` override: the shell adds the user's list to the session mode's
own (`/usr/share/gnome-shell/modes/ubuntu.json`), and the user can turn it
off in Extensions like any other.

### Decisions

- **A service, not a smart extension.** Shell extensions run inside
  gnome-shell; an exception there is a shell crash. The extension holds a
  D-Bus proxy and a menu, nothing else. The service is also what a
  settings panel, a CLI or another desktop could read.
- **What the user may see, nothing more.** The service never runs as root
  and asks for no token. Agent units are public on the system bus; the
  gateway's `routes` and the vault's `ledger` already filter for
  non-operators. An operator (root) would see more, but the session is
  not root. The consequence: alerts about an *agent's* budget belong to
  the agent's principal and are not in the user's list yet. Attributing
  agents to the person who owns them is the enrolment slice's job.
- **Vault grant prompts are not here yet.** The vault has no pending
  request state: a grant is made by the owner or an operator, or an agent
  is simply denied. Prompting the person when an agent asks is a vault
  feature (a request row, a notification with Allow/Deny, a grant with an
  expiry) and comes with desk enrolment, when agents have an owner.
- **Agent control through polkit.** Start and stop go to systemd on the
  system bus with `ALLOW_INTERACTIVE_AUTHORIZATION`; GNOME's polkit agent
  prompts for an administrator's password, as it does for `systemctl`.
  No MaluOS-specific polkit rule yet; a desk rule ("the console user may
  manage agents they own") also waits for ownership.

### The test

`tests/qcow2-boot-test.sh` now logs the test user straight into the
MaluOS session on desktop images (GDM `AutomaticLogin` written by the
NoCloud seed), waits for the graphical session, then as that user over
the session bus: the extension reports state ENABLED through
`org.gnome.Shell.Extensions`, the user unit is active, `GetState` shows
the gateway ok, the vault and the gateway seeing `user:maluos`, the
memory tenant and `VARIANT=Desktop`. It creates an agent `desk` without
starting it, checks the session sees it inactive, starts and stops the
unit with systemctl and checks the service saw both within thirty
seconds, then reads the service's journal for the three notifications
(created, running, stopped) and the absence of delivery errors. The
whole desktop session runs under software rendering in QEMU, so this is a
real GNOME session with the real shell loading the real extension.

Found on the way: the session service was the first client ever to call
the gateway before first boot had provisioned the database, and the
gateway answered that with a 500 and an "internal error" in its journal
(which the boot test treats as a failure). It now answers 503 `not_ready`
and logs "not ready" (maluos-gateway 0.3.2). And GNOME disables
extensions on the lock screen: the test session had idle-locked during
the ten minutes of server checks, so the extension read as DISABLED with
no error. The seed now writes a dconf system database that turns the idle
lock off for the test user before gdm starts.

## Slice 3 (2026-10-20): ownership, grant requests, the Desk window

```
maluctl agent create NAME ... [--owner user:NAME | --owner none]   default: the sudo user, when enrolled
  /etc/maluos/agents/NAME.env             MALUOS_AGENT_OWNER=user:NAME
  maluos_agent (tenant schema)            the registry: name, principal, owner, exec, sandbox, removed_at
  /etc/polkit-1/rules.d/60-maluos-agent-NAME.rules   the owner's session manages the unit, no admin password
maluos-vault 0.3.0: maluos_secret_request  a refusal files a pending request for the secret's owner
  GET /v1/requests  POST /v1/secrets/REF/request  POST /v1/requests/ID/approve|deny
  maluctl secret requests | request NAME | approve ID [--expires 7d] | deny ID
maluos-desktop-session 0.2.0: agents carry owner and mine; vault.requests; RequestDecide(id, approve|deny, expires)
  notifications with Allow and Deny buttons (org.freedesktop.Notifications actions)
maluos-desk (in maluos-desktop-session): the MaluOS Desk window, GTK 4 + libadwaita, com.maluos.Desk.desktop
```

Slice 2 showed the desk what the host knows. Slice 3 gives the person on
the desk a say: their agents are theirs, an agent that asks for one of
their keys gets an answer from them, and there is a window with room for
all of it.

**Ownership.** An agent belongs to a person. `maluctl agent create`
records the owner in the registry table `maluos_agent` in the tenant
schema (shipped with the vault's schema, since the vault is the first
consumer) and in the agent's env file, which the session reads without a
database connection. The default owner is the person running sudo, when
they are an enrolled principal; `--owner none` makes a system agent that
only operators manage. Two things follow from ownership. The vault scopes
a person's ledger view to their own rows, rows brokered for them, and the
rows of agents they own, so an agent's denials, uses and alerts reach its
owner's desk. And a polkit rule written per agent lets the owner's Linux
user start, stop and restart that one unit without an administrator's
password: `action.lookup("unit")` and `subject.user` are the whole test.
The rule is a file the agent's creation writes and its removal deletes;
polkit's JavaScript rules cannot read the registry themselves.

**Grant requests.** The vault had no pending state: an agent asking for a
key it was not granted was simply refused. Now the refusal itself files a
request. `maluos_secret_request` holds one pending row per secret and
requester; asking again bumps `asked_count` and keeps the first purpose
unless a new one is given. The owner (or an operator) approves, which
makes the grant with an expiry and records its id on the request, or
denies. A refusal in the day after a denial does not file again, so a
denied agent does not nag; an explicit `maluctl secret request` does. The
refusal's error body carries `request_id`, so a client (the gateway's
credential lookup, an agent's own code) can tell the person it has asked.
Requests are visible to their requester, to the owner who must decide,
and to operators.

**The session.** Every poll reads the pending requests; a new one for a
secret the session user owns becomes a notification with two buttons,
Allow for a week and Deny, through `org.freedesktop.Notifications`
actions. The service listens for `ActionInvoked` and answers the vault
as the user (peer credentials: the vault checks that the user owns the
compartment, the session asserts nothing). The indicator lists the
requests with the same choices plus Allow for a day, marks the user's
agents as theirs and sorts them first, and gains Open MaluOS Desk.

**The Desk window.** `maluos-desk` is a libadwaita application
(`com.maluos.Desk`) with four pages on the same D-Bus state: Agents (yours
first, with start, stop, restart and logs), Models (gateway, backends,
your policy and budget, recent calls), Vault (requests to decide with
Allow and Deny, your compartments, delegations, your own pending
requests), Alerts. It renders and forwards; `--self-test` builds the
window from the live state, prints a summary and exits, which is what the
boot test runs on the session's Wayland display.

### Decisions

- **Ownership lives in the tenant schema, not in polkit or a file alone.**
  The registry is what the vault reads for ledger scoping and what desk
  enrolment will carry to the office; the env file is a cache for the
  session; the polkit rule is derived from both and regenerated on every
  create.
- **The refusal files the request.** No agent needs new code to ask: the
  first time it reaches for a key the owner sees a prompt. An explicit
  request exists for agents that want to ask before they need it.
- **Allow means a week.** The notification's quick answer is a
  time-limited grant at the level the agent needed (`use` from the
  gateway, `read` from `maluctl secret show`); a longer or budgeted grant
  is a `maluctl secret approve` with its flags, or a delegation.
- **A GTK window, not a Settings panel.** GNOME Settings panels are
  compiled into gnome-control-center; a separate libadwaita application
  is what every other distribution-specific tool is, and it can follow the
  session service's state without a shell restart.

### The test

`tests/vault-local-test.sh` (85 checks) covers the request lifecycle on
the dev host: a refusal files, asking again bumps, the requester cannot
approve, the owner approves with an expiry and the requester then reads,
a denied request is not re-filed by the next refusal but is by an
explicit ask, request events in the ledger, and the owner's ledger view
gaining their agent's rows once the registry row exists.
`tests/qcow2-boot-test.sh` continues the slice 2 desktop section: the
desk agent's default owner and registry row, the polkit rule and a start
and stop of the unit by the user without sudo, the session marking the
agent as theirs, a user secret the agent is refused (request filed), the
session seeing the request and notifying, `RequestDecide` over the bus,
the grant existing and the agent reading the key, the decision in
`maluctl secret requests`, and `maluos-desk --self-test` on the session's
display.

## Slice 4 (2026-10-21): the logo

The first installs were made from an image whose wallpaper was a bare
gradient and whose login logo, distributor icon and boot-splash watermark
were a placeholder mark drawn in SVG. The MaluOS logo (the ring of blue
with the orange hexagons, the wordmark, the Kinetic Seas tagline) now
replaces the placeholder everywhere maluos-desktop-branding puts one.

- **One source, generated outputs.** The logo as supplied
  (`packages/maluos-branding/files/desktop/src/maluos-logo-full.png`,
  2024x777 RGBA, white wordmark on transparency) is committed, and
  `tools/make-branding.py` derives every asset from it, so a new logo
  file is one script run away from a rebuilt package. The derived files
  are committed too; the package build does not need PIL.
- **Wallpapers.** The logo sits a little above centre on the two
  gradients, 1000 px wide on the 2560x1600 canvas. The dark wallpaper
  carries the logo as supplied. For the light one the script recolours
  the white parts of the wordmark (the Malu letters and the tagline) to
  navy and leaves the emblem alone, since its white disc is part of the
  mark. `picture-uri` and `picture-uri-dark` under the `ubuntu` desktop
  section select them as before.
- **Login screen.** `org.gnome.login-screen logo` points at a 260x100 PNG
  of the full logo (Ubuntu's is 187x72; GDM shows the file at pixel size
  on its dark greeter).
- **Distributor icon.** `LOGO=maluos-logo` in os-release resolves to the
  emblem, squared and rendered at the hicolor sizes 16 to 512. The SVG
  mark is gone.
- **Boot splash.** The diverted spinner watermark is the full logo at
  280 px wide, white on transparency, which both the spinner theme and the
  bgrt theme (the default; it reads the spinner's image directory) draw
  near the bottom of the screen.

Not touched: the ISO's boot. The server live installer's initrd carries
only plymouth's text plugins, so the installer boots behind an "Ubuntu"
text splash and then runs subiquity; that is Ubuntu's squashfs and stays
so until the graphical live session (next slices).

## Slice 5 (2026-10-22): updates and software

Until this slice an installed MaluOS took no updates at all: the image
disabled `maluos.sources` ("no public mirror yet", from before
apt.maluos.com existed) and unattended-upgrades was only a Recommends of
maluos-base, which the rootfs build never installs (mmdebstrap's apt runs
without recommends; the same is true of every `?` line in the seeds). The
desktop had GNOME Web because Firefox on Ubuntu means the snap.

- **Updates reach installed systems.** `maluos.sources` stays enabled in
  the image (apt.maluos.com, production-signed, verified by the shipped
  keyring); the media copy (`maluos-iso.sources`, written by the
  installer) stays beside it. maluos-base now *depends* on
  unattended-upgrades, and the MaluOS policy
  (`52maluos-unattended-upgrades`) covers Ubuntu's security pocket, the
  MaluOS repository and Mozilla's repository, the last by
  `Origins-Pattern "site=packages.mozilla.org"` because Mozilla's Release
  file carries an opaque registry path as its Origin. Everything else
  waits for the user.
- **Firefox from Mozilla.** maluos-archive 0.3.0 adds a second binary
  package, maluos-archive-mozilla: the deb822 source for
  packages.mozilla.org, Mozilla's signing key vendored as
  `keys/packages.mozilla.org.asc` and checked against the published
  fingerprint (35BA A0B3 ... DC63 15A3) when the package builds, and a
  pin that puts Mozilla's packages at 1000 and Ubuntu's snap-transitional
  `firefox` (epoch 1, which would otherwise win) at -1. The desktop seed
  takes firefox from there and drops epiphany-browser; Ubuntu's
  `ubuntu-mimeapps.list` already prefers `firefox.desktop`, so Firefox is
  the default browser without a MaluOS override. Building the image needs
  Mozilla's repository reachable: `image/profiles/desktop.pkgs` lists
  maluos-archive-mozilla, and stage-packages.sh installs any
  `maluos-archive-*` entry first and refreshes apt before the profile.
  The installer is unaffected: an unreachable source is a warning to
  `apt-get update`, and `tests/iso-apt-check.sh` still passes offline.
- **GNOME Software, deb plugin only.** gnome-software with
  gnome-software-plugin-deb and appstream, no snap or flatpak plugin.
  PackageKit does the offline updates and asks polkit, so an active local
  user installs updates without sudo. One gsettings override
  (`download-updates-notify=false`) leaves the notification to the
  session.
- **`maluctl update`.** A maluctl plugin in maluos-firstboot 0.1.7
  (python3-apt): `status [--json]` lists pending updates with their source
  (security, maluos, mozilla, ubuntu, other), which of them the automatic
  policy will install, when the lists were last refreshed, when the last
  automatic run was, whether a restart is due; `check` runs apt-get
  update, `apply` runs unattended-upgrade in the foreground (`--all`:
  apt-get full-upgrade), `history` shows the automatic runs and apt's
  history. `status` needs no privileges, so the session can use it.
- **The session.** maluos-desktop-session 0.3.0 reads
  `maluctl update status --json` whenever apt's or dpkg's state changes
  on disk (stat of five paths each poll) and every 15 minutes otherwise.
  Updates that wait for the user become one notification per set, with
  Install opening GNOME Software's updates page; a due restart becomes one
  with Restart (gnome-session-quit). `UpdateAction(open|restart|refresh)`
  is on the bus; the indicator shows an Updates line with the pending
  list and the same actions; the Desk gains a System page. The reading
  has its own thread: the first desktop boot test (0.3.0) ran it in the
  poll thread, where a 90-second apt cache open under emulation stalled
  the agent and request checks that followed; 0.3.1 never lets it block
  the poll loop or the bus, and `Refresh()` no longer forces it.

### Decisions

- Mozilla's repository, not a MaluOS rebuild of Firefox: Mozilla signs
  and ships within hours of a release, and the key is pinned at build.
- The media's package copy stays installed as a source: offline installs
  still get `apt install` of what the image carried, and apt picks the
  newer of media and mirror.
- Seeds' `?` lines are documented as not reaching images. Whether the
  desktop should install its recommends (ibus, cups, fwupd,
  qemu-guest-agent are all missing today) is a separate decision.

### The test

Every image: unattended-upgrades installed, the policy names MaluOS and
Mozilla, both apt-daily timers enabled, maluos.sources enabled,
`maluctl update status` works without privileges and its JSON says the
automatic policy is on. The desktop: firefox is Mozilla's deb (version
without "snap", maintainer Mozilla), the source, keyring and pin are in
place, apt's candidate for firefox comes from packages.mozilla.org (a
warning when the VM has no route to Mozilla), gnome-software with the deb
plugin and neither the snap nor the flatpak plugin, the session's state
carries `updates` with the automatic policy on and no restart due, and
`UpdateAction refresh` re-reads within a minute.

## Slice 6 (2026-10-22): desk enrolment

```
sudo maluctl office enroll https://app.example.com --code 7F3K-2Q9M [--name "Ed's desk"]
  vault user:<login>/office-desk-token        the desk token, the person's, use by the gateway, read by grant
  /etc/maluos/office.yaml, office.env         the office, the desk, the owner, the endpoints; MALUOS_OFFICE_* for agents
  gateway backend/tier/alias office           the office's model endpoint as a rung: --model office, applied with the token
maluctl office status [--live] | heartbeat | sudo maluctl office leave
maluos-desktop-session 0.4.0: office in the state; heartbeats every heartbeat_s; offline on SIGTERM; OfficeAction(open|heartbeat)
python3 -m maluos_desk.mock_office            the contract's reference office for tests (docs/desk-enrolment.md)
```

The desk joins the office. The Business OS kernel's estate already has the
desk as a location kind, with an owner, an enrolment token, presence and a
last-seen time, and its own plan put the enrolment API at stage D2, behind
the owner's approval of schema and endpoints. This slice fixes the
contract between the two (docs/desk-enrolment.md, surface 1: enroll with a
one-time code, heartbeat, me, leave), builds the whole desk side in a new
package, `maluos-desk`, and proves it against a mock office that
implements the contract; the kernel half is a spec in the kernel
repository (`docs/build-specs/desk-enrolment.md` there: one additive
migration, four endpoints, the allow-list line, the presence job) for the
owner to approve.

**What enrolment is.** A person gets a one-time code from the office and
runs `sudo maluctl office enroll URL --code CODE`. The desk posts the code
and its facts; the office makes the desk location under the person's name
and answers with a desk token and its endpoints. The token goes into the
person's own vault compartment, as their Anthropic key would, so grants,
delegations, the ledger and requests all apply; nothing is written to a
file. The office's model endpoint becomes a rung of the desk's gateway
(`openai_compat` with the token as its secret): `--model office` sends a
call to the office's ledger proxy as the person, an agent gets there only
through the person's delegation, and the office's rules hold on a desk
(no provider key here, every call in the office's prompt ledger). The
office's MCP endpoints are in `/etc/maluos/office.env` for every agent
unit; an agent that should read the office's records or memory needs a
`read` grant on the token, a decision the owner makes per agent.

**Presence.** The session service heartbeats the office while the person
is signed in and says offline when it stops (SIGTERM at logout). The
office's Work Locations shows the desk online or offline; the indicator
shows "Office: Subello · online" with Open office and Check in now; the
Desk's System page has an Office group. When the office retires the desk,
the next heartbeat gets 410: the session tells the person, `maluctl office
status` says RETIRED, and `sudo maluctl office leave` removes the token,
the rung and the files.

### Decisions

- **A code, not a password.** The office mints a short-lived single-use
  code for a person; neither side ever sees the other's password. It is
  how Ubuntu Pro attaches a machine.
- **The token is the person's, in their vault.** `use` by the gateway on
  their behalf, `read` by the owner or by an explicit grant; the ledger
  names every use. A desk gives the office nothing the person did not.
- **The office is a cloud rung, not a peer gateway.** The kernel's desk
  plan already names a platform-hosted model endpoint; treating it as an
  `openai_compat` backend keeps the ladder, the sensitivity gate, budgets
  and the local ledger unchanged. Peer gateways (Phase 9 FR-21) are a
  fleet sharing GPUs, a different thing. One consequence: the gateway
  counts the office as leaving the host, so an agent reaches the office
  rung only when an operator has raised its egress ceiling (`maluctl
  gateway policy set --principal agent:NAME --egress internal`) on top of
  the owner's delegation; a person's own calls pass at the default.
- **Presence is the session, not a timer.** A headless host is not a desk;
  the heartbeat is the person's, with their token, while they are signed
  in. The service reads the token from the vault once per enrolment and
  passes it to `maluctl office heartbeat` in the environment, so the vault
  ledger does not grow by a row every five minutes.
- **The kernel half followed the owner's approval, the same day.** db/187,
  four PHP endpoints, the Desks section of Settings with the one-time
  code, `bin/mint_desk_code.php`, the presence sweep, the allow-list
  lines, a 39-check proof. The office publishes no model, memory or
  actions endpoints to desks yet (null in its answer), so a real
  enrolment makes no gateway rung until that kernel slice; the mock

### Slice 7 (planned 2026-10-23): power defaults, Tools Installer, MaluApps, Credential Manager, Upgrade Manager

**1. Power defaults that keep agents alive.** GNOME's defaults blank the
screen after 5 minutes and suspend the machine after 20 minutes on
battery (and on the login screen, even on mains): a suspended desk
terminates every agent, gateway call and office heartbeat on it. The
desktop ships with Automatic Screen Blank off and Automatic Suspend off,
on battery and plugged in, in the user session and on the greeter:

```
# packages/maluos-branding/files/desktop/20_maluos-desktop.gschema.override (maluos-desktop-branding)
[org.gnome.desktop.session:ubuntu]
idle-delay = uint32 0                       # Settings → Power → Automatic Screen Blank: Never
[org.gnome.settings-daemon.plugins.power:ubuntu]
sleep-inactive-ac-type = 'nothing'          # Automatic Suspend, plugged in: off
sleep-inactive-battery-type = 'nothing'     # Automatic Suspend, on battery: off
[org.gnome.settings-daemon.plugins.power:GNOME-Greeter]
sleep-inactive-ac-type = 'nothing'          # GDM suspends an idle login screen after 20 min by default
sleep-inactive-battery-type = 'nothing'
```

These are defaults, not locks: a person can turn blanking or suspend back

| Page | What you do there | CLI |
|---|---|---|

### Slice 8 (planned 2026-10-23): the Agents app and the agent icons

Requested by the owner on 2026-10-23: the agents a person can use,
local and remote, as icons on the desktop or in an "Agents" folder, and
one management application to talk to an agent and control it. The
Business OS kernel already has a browser-based agent management at the
office's `os.` address; on the desktop the owner wants an application in
its own window, "something like an Electron application", not a browser
tab. It works the same for an agent on this desk and one on an office
server.

**The icons.** Two places, one source. The session keeps a launcher per
agent (`~/.local/share/applications/maluos-agent-<id>.desktop`, with the
agent's icon and name, `Exec=maluos-agents --agent <id>`) in sync with
the agent list: the local agents the person owns or may use (`maluctl
agent list`, filtered by the vault's grants as the Desk's Agents page is)
and, on an enrolled desk, the office's directory (Phase 13 slice 2; until
then the office's agents listed by its `me` answer). GNOME shows them in
an "Agents" app folder in the grid (`org.gnome.desktop.app-folders`,
folder `maluos-agents`, written by the session), and on the desktop
itself through Ubuntu's desktop-icons extension
(`gnome-shell-extension-desktop-icons-ng`, in the archive, not yet in the
desktop seed), which shows `~/Desktop`: the session puts an "Agents"
folder there holding the same launchers, so the person sees agents on
their desktop and in the grid without two lists to maintain. An agent
that goes away takes its icon with it.

**The application: `maluos-agents`.** One window, one list on the left
(local agents, then the office's, with presence and state), and for the
selected agent:

| Page | Local agent (this desk) | Remote agent (an office server) |
|---|---|---|
| Talk | a conversation with the agent: tasks sent and answers received, with the ledger rows each answer caused and the files or records it touched | the same, through the office |
| Control | start, stop, restart, the unit's logs live, `run` a one-off command | start, stop, restart and logs as the operator's authority allows (Phase 13 slice 2 envelope) |
| Policy | class, tiers, backends, cloud, egress, budget and what is used of it; the delegations the agent holds (use-only keys) and the scopes it reads | read; edits where the kernel's Agent HR allows |
| Memory | what the agent remembers in its compartment and scopes, as claims with provenance | the same, through the office's `memory` endpoint (Phase 13 slice 4) |
| Activity | the audit trail: calls, grant requests, tasks delegated and received | the same |

One protocol for both columns: the A2A-compatible task interface that
Phase 13 slice 2 puts on every node. `maluos-agent` serves it for the
local agents over a Unix socket (peer credentials, no token), the office
serves it for its agents over HTTPS with the desk token; the app does
not know or care where an agent runs except to show it. Until slice 2
exists, the local column works over the session's D-Bus (the Desk's
`AgentAction` today) and the remote column is read-only from the office's
`me` and `activity` endpoints.

**Why not Electron itself, and what instead.** Electron bundles a
Chromium and a Node runtime (about 250 MB per application), is not in
Ubuntu's archive, and would be the one component of the desktop built
from an upstream tarball rather than a Debian package; it also puts a
second browser engine beside Firefox for the security team to track. The
same kind of application, a web UI in its own window with native
integration, is what Tauri or a WebKitGTK shell gives: the archive's
WebKitGTK 6.0 (the engine behind GNOME's own Web and Software), a few MB,
packaged like everything else, with the same JavaScript UI code. The
plan therefore is **a web-technology application in a WebKitGTK window**:
the UI is HTML/JS, which the kernel's browser-based management and this
app can share (the office's agent pages are loaded in the same window
for remote agents, so one UI does not have to be written twice), and the
native side (the window, the Unix socket, D-Bus, notifications, the vault
approvals) is the Desk's Python/GTK. Decision for the owner: this, or
Electron proper packaged by us. Both give "an Electron-like application";
only the first stays inside the distribution's packaging and update model.

**Packages:** maluos-agents (new: the app, the launcher writer, the app
folder and the desktop folder), maluos-desktop-session (agent list
changes trigger the launcher sync), maluos-meta (the desktop depends on
maluos-agents and the desktop-icons extension), maluos-agent (the local
A2A socket, with Phase 13 slice 2). Boot test: two local agents and the
mock office's agents produce the launchers, the app folder and the
desktop folder; the app starts, lists them, starts and stops a local
agent, and shows a remote agent's activity.

### The first external desktop install (2026-10-20)

The released desktop ISO (26.04.20261020) crashed in the installer on a
laptop and then on Proxmox at the same point: curtin's
`install_missing_packages` step, which installs into the target what the
chosen storage layout needs. The guided layout uses LVM, so curtin ran
`apt-get install lvm2` in the target, and the target had only the ISO's
pool as a source (the installer keeps the network sources off until the
end). The desktop image had no lvm2 (ubuntu-minimal pulls none of the
storage tools that ubuntu-server-minimal does) and the stock Ubuntu
Server pool does not carry it either: "Package 'lvm2' has no installation
candidate", exit 100, crash dialog. The boot tests never saw it because
the qcow2 skips the installer.

Fix: the desktop profile lists lvm2, cryptsetup, mdadm, btrfs-progs and
xfsprogs, so every layout subiquity offers except ZFS needs nothing from
apt. `tests/iso-apt-check.sh` now works offline exactly as curtin sees
the target and simulates installing curtin's storage and boot packages;
it fails on the released desktop ISO and passes on the server ISO and the
rebuilt desktop ISO. The rebuilt image also passed the UEFI boot test
(139 checks, the slice 3 checks among them). Workaround on the released
ISO: on the Storage screen untick "Set up this disk as an LVM group"
(plain ext4 needs nothing extra).
